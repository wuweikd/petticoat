# 0003-衣橱条目状态机与预订记录

## 状态：已接受

## 背景

全局变体与用户衣橱分离之后，仍需决定：同一用户对同一变体能否有多条记录、主状态如何升降、定金/尾款如何挂接。若建模过重（多条目、出柜状态、与电商订单同名），会偏离 Phase 1「个人记账工具」定位，并与「不做交易」冲突。

## 决策

1. **(User, Variant) 唯一**：同一用户对同一变体最多一条 **WardrobeEntry**；件数用数量字段表达。
2. **主状态最高水位**：想要 < 预订中 < 已拥有；默认只升不降。已拥有后再订同款不降回预订中，追加预订挂在同一条目上。允许跳级升至已拥有（二手/现货）。
3. **取消预订是唯一降级例外**：主状态仍为预订中且从未到货时，取消后降回想要；已拥有下取消只关闭对应预订记录。
4. **PreorderRecord 一对多**：一条 WardrobeEntry 可挂多笔预订记录（首次与再贩追加）；未结清的参与尾款统计与日历，不要求主状态必须为预订中。英文避免使用 Order，以免与电商订单混淆。
5. **MVP 不做「已出柜」状态**：卖掉/送出由用户删除条目或改回想要。
6. **到货结清**：确认某笔 PreorderRecord 到货后归档该笔；主状态若尚非已拥有则升为已拥有且数量保持（默认 1）；若已是已拥有（追加再订）则数量 +1。

## 理由

- 唯一条目保证「同款连接 / 想要同款」语义简单，统计不双计
- 最高水位符合「柜子里已经有」的直觉，同时仍能用预订记录盯尾款
- 一对多预订记录覆盖再贩，又不必拆多条衣橱条目
- 出柜/转卖一旦产品化，易滑向交易与成色市场，留给后续阶段显式决策

## 后果

- 「已拥有又再订」时，三分区归类看主状态，尾款列表看未结清 PreorderRecord——两套视图必须同时做对
- 首次到货升已拥有时数量不自动 +1（避免与默认数量 1 双计）；仅已拥有后再到货才 +1
- 取消降级与「只升不降」并存，文档和校验都要显式写出例外
